# Общие задачи в самостоятельном Дашборде

## Доступ и интерфейс

Раздел «Задачи» открыт пользователям с действующей сессией Supabase Auth. Новые аккаунты получают доступ после входа. Все доски общие. Статус задачи соответствует названию колонки. Список, Канбан и Гант показывают одни данные. Закрытые доски, приглашения и роли отложены.

Согласованный интерфейс находится в `src/app/pages/TasksPage.tsx` и `src/app/tasks/`. В самостоятельном Дашборде используется клиент Supabase. Корпоративная сборка использует свой API Hermes и SQLite. Базы двух развёртываний самостоятельны.

## Данные

Миграция создаёт хранилище в PostgreSQL Supabase. Фронтенд загружает и сохраняет данные через RPC `dashboard_tasks_list`, `dashboard_tasks_create` и `dashboard_tasks_save`. Запросы без сессии отклоняются. Ответственный хранится как стабильный идентификатор пользователя. Список назначений возвращает отображаемые имена без адресов электронной почты.

Сохранение проверяет ревизию доски. После конфликта клиент предлагает обновить данные. Повтор создания с тем же идентификатором безопасен. Дата выполнения ставится сервером по Москве при переводе в колонку завершения. По прошествии 10 календарных дней выполненная задача отображается в архиве. Статистика учитывает фильтры и выбранный период по сроку или дате выполнения. Процент выполнения в срок считается только по выполненным задачам с заданным сроком.

## Релиз и откат

1. Влить PR в `main` на GitHub. На VPS получить точный SHA этого релиза. Для сборки извлечь исходники через `git archive` в отдельный каталог. Сборка использует параметры действующего VPS и включённый экран входа.
2. Проверить сборку, наличие хешированных CSS и JS и доступность места для резервной копии. Применить SQL из того же коммита через `psql -X -v ON_ERROR_STOP=1` в контейнере `supabase-db`. Миграция транзакционная. Обновить кэш схемы PostgREST.
3. Сохранить предыдущий `dist/index.html`, разместить новые хешированные файлы рядом со старыми и атомарно заменить точку входа. Старые файлы нужны уже открытым вкладкам.
4. Проверить страницу входа, доступ к `/tasks`, создание задачи, чтение и изменение из второй сессии. Проверить отказ прямого RPC без сессии, повторное чтение после перезагрузки и горизонтальную прокрутку Канбана на мобильной ширине.
5. Для отката фронтенда атомарно восстановить прежний `index.html` из резервной копии. Данные новых досок сохраняются в PostgreSQL для следующей выкладки.
